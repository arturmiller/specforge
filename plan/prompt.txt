Du bist Principal Software Architect, Knowledge-Representation Engineer und AI Coding Agent. Deine Aufgabe ist es, einen prototypischen „Requirements & Compliance Compiler“ zu entwerfen und anschließend zu implementieren.

## Ziel

Ich möchte Software nicht primär aus freien Prompts generieren, sondern aus einer Kombination aus:

1. produktspezifischen Anforderungen,
2. Domänenwissen,

4. regulatorischen Anforderungen,
5. technischen Implementierungsmustern.

Das System soll aus diesen Eingaben eine aufgelöste Systemspezifikation erzeugen und daraus Software, Tests und nachvollziehbare Compliance-Evidenz ableiten können.

Der erste vollständige Use Case soll eine kleine Kalender-Webanwendung sein.

# 1. Grundidee

Das System soll sich eher wie ein Compiler als wie ein klassischer Codegenerator verhalten.

Konzeptionelle Pipeline:

```text
Product Intent
      ↓
Product Model / Product Requirements
      ↓
Semantic Enrichment
      ↓
Ontology / Domain Knowledge
      ↓
Rule Resolution
      ↓
Derived Requirements
      ↓
Resolved System Specification
      ↓
Architecture / Implementation Patterns
      ↓
Code + Infrastructure + Tests
      ↓
Validation
      ↓
Compliance / Traceability Evidence
```

Der entscheidende Punkt ist:

Ein Entwickler oder Agent soll nur die produktspezifische Absicht definieren müssen.

Querschnittsanforderungen sollen von spezialisierten Teams zentral gepflegt werden können.

Beispiele:

* Security
* Datenschutz / DSGVO
* Accessibility
* Observability
* Architektur
* Plattformvorgaben
* später regulatorische Domänen wie MaKo

Diese Anforderungen sollen automatisch auf Produkte angewendet werden.

# 2. Beispiel für die gewünschte Ableitung

Angenommen, die Produktspezifikation beschreibt:

```text
Calendar

Entity:
Event

Event contains:
- title
- description
- participants
- location

Feature:
User can view own events.
```

Das System soll semantisch erkennen können:

```text
Participant
→ Person
→ PersonalData
```

Daraus sollen Regeln beispielsweise ableiten:

```text
Event contains PersonalData
→ access requires authentication

Event belongs to User
→ access requires authorization

PersonalData
→ transport encryption required

PersonalData
→ privacy requirements apply
```

Dadurch entstehen automatisch zusätzliche Anforderungen.

Beispiel:

```text
PRODUCT-001
User can view own events.

SEC-001
Access to resources containing personal data requires authentication.

SEC-002
A user may access only resources they are authorized to access.

PRIVACY-001
Personal data must have an identified processing purpose.
```

Die finale Systemspezifikation könnte dann beispielsweise enthalten:

```yaml
endpoint:
  method: GET
  path: /events/{id}

resource:
  type: Event
  classification:
    - PersonalData

requirements:
  - PRODUCT-001
  - SEC-001
  - SEC-002
  - PRIVACY-001

controls:
  authentication: required
  authorization:
    type: ownership
```

# 3. Trennung der Verantwortlichkeiten

Das System soll unterschiedliche „Owner“ für Wissen unterstützen.

Beispielsweise:

```text
product/
security/
privacy/
platform/
architecture/
domain/
```

Diese Bereiche sollen logisch und möglichst auch technisch getrennt sein.

Langfristig sollen unterschiedliche Teams eigene Repositories pflegen können.

Beispiel:

```text
security-rules repository

privacy-rules repository

platform-patterns repository

calendar-product repository
```

Das Produktteam darf die Security-Regeln nicht verändern.

Ein Coding-Agent soll gegebenenfalls Schreibzugriff auf den Anwendungscode haben, aber nur Lesezugriff auf zentrale Compliance-Regeln.

Berücksichtige deshalb Versionierung, Ownership und Dependency Management bereits im Design, auch wenn der erste Prototyp zunächst in einem Monorepo umgesetzt wird.

---

# 4. Anforderungen versus Implementierungsmuster

Trenne strikt zwischen:

## Requirement

Beispiel:

```text
Resources containing personal data require authenticated access.
```

und:

## Implementation Pattern

Beispiel:

```text
For REST APIs:
JWT authentication via an API gateway or application middleware satisfies authentication requirement SEC-001.
```

Eine fachliche oder regulatorische Regel darf nicht direkt von einer bestimmten Technologie wie OAuth, Cognito, Keycloak oder AWS API Gateway abhängen.

Technologien sollen austauschbare Implementierungsmuster sein.

# 5. Ontologien

Prüfe kritisch, an welchen Stellen echte Ontologien sinnvoll sind.

Nutze Ontologien insbesondere für:

* Begriffe,
* Typen,
* Taxonomien,
* Beziehungen,
* semantische Vererbung,
* Ableitung von Eigenschaften.

Beispiele:

```text
IBAN
isA FinancialIdentifier

FinancialIdentifier
isA PersonalData
```

oder:

```text
EventParticipant
isA Person

Person
has PersonalData
```

Versuche NICHT, sämtliche Regeln zwanghaft in OWL/RDF auszudrücken.

Erkläre, welche Teile sinnvollerweise über:

* RDF/OWL,
* SHACL,
* eigene Regel-DSL,
* Datalog,
* OPA/Rego,
* DMN,
* Python-Regeln

abgebildet werden sollten.

Wähle für den MVP die pragmatischste Lösung.

Das System soll nicht akademisch komplexer sein als notwendig.

---

# 6. Expertensystem / Rule Engine

Ein zentraler Bestandteil soll ein deterministischer Requirement Resolver sein.

Konzeptionell:

```text
Facts
+
Ontology-derived facts
+
Rules
=
Derived Requirements
```

Beispiel:

```text
FACT:
Endpoint returns Event

ONTOLOGY:
Event contains Participant
Participant is Person
Person is PersonalData

DERIVED FACT:
Endpoint returns PersonalData

RULE:
IF
  endpoint exposure == external
  AND endpoint returns PersonalData
THEN
  require Authentication
```

Der Resolver soll deterministisch arbeiten.

LLMs dürfen NICHT entscheiden, ob eine formalisierte Security-Regel erfüllt ist.

LLMs können unterstützen bei:

* Extraktion,
* Übersetzung natürlicher Sprache in formale Modelle,
* Codegenerierung,
* Erklärung,
* Vorschlägen.

Aber die eigentliche Auswertung formalisierter Regeln soll reproduzierbar und deterministisch sein.

---

# 7. Declared und Derived Requirements

Unterscheide explizit zwischen:

## Declared Requirements

Vom Produktteam direkt angegebene Anforderungen.

Beispiel:

```text
User can create an event.
```

## Derived Requirements

Durch Regeln automatisch abgeleitete Anforderungen.

Beispiel:

```text
Creating an event requires authentication.
```

Jede abgeleitete Anforderung muss erklären können:

* warum sie gilt,
* aus welcher Regel sie stammt,
* welche Fakten die Regel ausgelöst haben,
* welche Quelle die Regel besitzt,
* welche Implementierung sie erfüllt,
* welche Tests bzw. Evidenzen sie verifizieren.

---

# 8. Traceability Graph

Das System soll einen nachvollziehbaren Graphen erzeugen.

Beispiel:

```text
Security Policy
       ↓
SEC-001
       ↓
applies because
       ↓
Event contains PersonalData
       ↓
implemented by
       ↓
JWT Authentication Middleware
       ↓
verified by
       ↓
test_anonymous_user_cannot_read_event
       ↓
PASS
```

Eine zentrale Frage des Systems soll beantwortbar sein:

```text
Warum gilt diese Anforderung?
```

und:

```text
Warum betrachtet das System diese Anforderung als erfüllt?
```

Ein Requirement darf nicht einfach den Status „compliant“ erhalten.

Stattdessen sollen beispielsweise Statuswerte existieren wie:

```text
NOT_EVALUATED
REQUIRED
IMPLEMENTED
VERIFIED
FAILED
HUMAN_REVIEW_REQUIRED
```

---

# 9. Grenzen des Compliance-Nachweises

Das System darf niemals pauschal behaupten:

```text
Die Anwendung ist DSGVO-konform.
```

Stattdessen soll es präzise Aussagen treffen können wie:

```text
Alle für dieses System formalisierten und automatisch verifizierbaren Anforderungen wurden erfolgreich geprüft.
```

Bestimmte Anforderungen müssen als nicht vollständig maschinell entscheidbar markiert werden können.

Zum Beispiel:

```yaml
verification:
  type: human_review
```

oder:

```text
PARTIALLY_VERIFIABLE
```

Dies ist insbesondere für unbestimmte Rechtsbegriffe wichtig, z. B.:

* angemessen,
* erforderlich,
* verhältnismäßig,
* Stand der Technik.

---

# 10. Softwareänderungen ohne Spec-Änderung

Das System soll ausdrücklich erlauben, Implementierungsdetails zu ändern, ohne die Produktspezifikation anzupassen.

Beispiel:

```text
Agent, mache den Button grün.
```

Das soll lediglich eine Codeänderung auslösen.

Danach soll erneut validiert werden, dass alle relevanten Anforderungen weiterhin erfüllt sind.

Das System soll zwischen ungefähr folgenden Arten von Änderungen unterscheiden können:

```text
Non-semantic implementation change

versus

Semantic system change
```

Beispiele für non-semantic:

* Farbe,
* Layout,
* internes Refactoring,
* Umbenennung interner Variablen.

Beispiele für semantic:

* Endpoint wird öffentlich,
* neues personenbezogenes Datenfeld,
* Berechtigung wird geändert,
* API-Verhalten wird verändert.

Es muss nicht sofort perfekte automatische Change Classification geben.

Entwirf aber die Architektur so, dass Impact Analysis später möglich ist.

---

# 11. Incremental Validation / Impact Analysis

Langfristig soll der Knowledge Graph erkennen können, welche Regeln und Tests durch eine Änderung betroffen sind.

Beispiel:

```text
Button CSS changed
→ UI tests
→ accessibility checks

API authorization changed
→ product requirements
→ security requirements
→ privacy requirements
→ authorization tests
```

Der MVP darf zunächst alles neu validieren.

Die Architektur soll aber spätere inkrementelle Auswertung ermöglichen.

# 14. Generator

Für den ersten MVP muss der Compiler nicht beliebige Anwendungen generieren können.

Es reicht, wenn er beweist, dass das Konzept funktioniert.

Er soll mindestens:

1. eine Product Spec einlesen,
2. Ontologie-/Semantikwissen anwenden,
3. Regeln auswerten,
4. Derived Requirements erzeugen,
5. eine Resolved System Specification erzeugen,
6. daraus die Kalenderanwendung oder wesentliche Teile generieren,
7. Tests generieren oder auswählen,
8. Tests ausführen,
9. Evidence erzeugen,
10. einen nachvollziehbaren Compliance-/Requirement-Report erstellen.

# 15. Codegenerierung

* Templates,
* AST-basierte Generatoren,
* deklarative Generatoren,

# 16. Validierung

Der Compiler soll zwischen zwei Dingen unterscheiden:

```text
Requirement Resolution

und

Implementation Verification
```

Requirement Resolution beantwortet:

```text
Welche Anforderungen gelten?
```

Implementation Verification beantwortet:

```text
Sind diese Anforderungen durch die aktuelle Implementierung nachweislich erfüllt?
```

Beispiel:

```text
SEC-001:
Authentication required

Implementation:
JWT middleware

Verification:
integration test rejects anonymous request

Result:
VERIFIED
```

---

# 17. Tests als Evidenz

Tests sollen selbst Teil des Modells sein.

Beispiel:

```text
Requirement SEC-001
verifiedBy TEST-SEC-001-01
```

Der Testlauf erzeugt eine konkrete Evidence:

```text
Evidence:
TEST-SEC-001-01
commit: abc123
timestamp: ...
result: PASS
```

Berücksichtige, dass Tests keine vollständigen mathematischen Beweise darstellen.

Das System soll transparent machen, welche Art von Evidenz vorliegt.

Ich möchte nicht, dass du einfach RDF, Neo4j, Drools oder irgendein anderes Tool auswählst, weil es zum Thema passt.

Bewerte zunächst:

* Was brauchen wir tatsächlich?
* Was ist für den MVP die einfachste belastbare Lösung?
* Wo benötigen wir echte semantische Inferenz?
* Wo reichen normale typisierte Datenstrukturen?
* Wo brauchen wir eine Regel-Engine?

# 27. Leitprinzipien

Behalte während des gesamten Projekts diese Prinzipien bei:

```text
Requirements are first-class objects.

Rules are owned independently from products.

Compliance requirements are injected, not copied.

Derived requirements must be explainable.

LLMs propose; deterministic systems decide.

The specification defines invariants, not every implementation detail.

Implementation may vary as long as invariants remain satisfied.

No compliance claim without evidence.

Every evidence must be traceable to a requirement and a concrete software version.

Human judgment must remain explicit where deterministic verification is impossible.
```

Das Ziel des MVP ist nicht, bereits ein universelles Legal-Tech-System zu bauen.

Das Ziel ist, anhand einer Kalenderanwendung überzeugend zu demonstrieren, dass eine kleine Produktspezifikation mit zentral gepflegtem semantischem Wissen und Regeln zu einer nachvollziehbaren, ausführbaren und überprüfbaren Systemspezifikation aufgelöst werden kann.
